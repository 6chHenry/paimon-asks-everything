# 版本预热与发行洞察内容设计

## 设计状态

- 状态：已确认设计基线
- 日期：2026-07-10
- 范围：版本预热、发行洞察
- 本轮原则：内容优先，UI 只做承载内容所必需的调整

## 1. 目标与边界

本次调整不改变五个页面的整体导航，也不处理版本情报首页、问派蒙和能力预览的主要体验。

本次只解决两个问题：

1. 版本预热目前更像资料展示，需要变成有节奏、有悬念的版本理解路线。
2. 发行洞察目前有统计和评分基础，需要变成可以服务版本筹备会的真实决策简报。

两页之间形成如下闭环：

```text
玩家进入预热专题
  → 选择理解深度、查看事件链和关系节点、继续追问
  → 产生主题与理解断点信号
  → 发行洞察聚合信号
  → 输出制作组下一步的内容动作与验证方法
```

## 2. 版本预热设计

### 2.1 页面职责

版本预热是面向玩家的编辑型内容体验，不是百科资料库，也不是问派蒙的替代品。

它要让玩家经历一条有方向的路线：

1. 先遇到一个版本悬念；
2. 回顾已经确认的事件；
3. 看到可以继续推演的暗示；
4. 在一个明确的未解断点处停下；
5. 带着具体问题继续等待版本开启或询问派蒙。

### 2.2 专题组织

保留现有三个专题，但将它们组织为同一条主悬念的三个观察角度：

| 专题 | 玩家入口问题 | 主要回答方向 |
|---|---|---|
| 七枚神之心的流转 | 最后一段流转会如何完成？ | 发生了什么 |
| 愚人众为何收集神之心 | 收集完成后真正要启动什么？ | 为什么做 |
| 冰之女皇的目标 | 她准备为此承担什么代价？ | 已知与未知 |

三个专题不各自制造互不相关的谜题，而是共同指向一个版本级主断点。这样玩家切换专题时会感到自己在从不同角度逼近同一个答案。

### 2.3 内容状态

每个专题的内容按三种状态编排：

#### 已确认

- 展示正式事件、人物行为和可靠来源。
- 使用确定语气。
- 允许进入时间线、关系图和证据详情。

#### 暗示线索

- 展示可以支持进一步推理的文本、关系或跨版本连接。
- 明确标注这是暗示、推论或证据边界，不写成已确认结论。
- 可以展开来源，但不能替玩家宣布最终答案。

#### 未解断点

- 明示具体问题，隐藏答案。
- 展示前置线索、当前已知边界和解锁条件。
- 不使用没有含义的灰色空白，也不提前填入版本开启后的答案。

断点卡片的固定内容结构为：

```text
问题：收集神之心最终要启动什么？
前置线索：已经确认的行动、相关人物、跨版本连接
当前边界：现有资料只能证明到哪里
状态：答案将在至冬版本开启后揭晓
行动：查看已确认事件 / 继续询问派蒙
```

### 2.4 页面叙事顺序

不大改现有 UI 结构，主要调整文案和内容层级：

1. 主题导语：用一句悬念提出主问题，并说明玩家将看到什么。
2. 理解承诺：告诉玩家看完后能确认哪些事情，但不会提前揭晓什么。
3. 事件链：从已确认事件开始，逐步过渡到暗示线索。
4. 断点节点：在时间线末端或关键关系处显示明示问题、隐藏答案。
5. 继续探索：提供与断点直接相关的派蒙问题，而不是泛化的“了解更多”。

### 2.5 深度与剧透边界

现有两种深度继续保留：

- **已过剧情回顾**：按玩家进度展示已确认事件，锁定后续地区。
- **完整考据**：展示已实装后续内容、文本暗示和争议边界，但仍不展示未实装版本的答案。

“完整考据”意味着更完整地讨论已存在的证据，不意味着允许页面替未来版本补写结论。

### 2.6 预热交互信号

继续记录以下行为，用于发行洞察：

- 进入了哪个专题；
- 选择了哪种深度；
- 打开了哪些时间线节点；
- 打开了哪些关系节点；
- 是否从专题继续提出问题。

后续可以增加“断点打开”或“继续提问”事件，但第一阶段不要求新增复杂埋点，先复用现有信号完成内容闭环。

## 3. 发行洞察设计

### 3.1 页面职责

发行洞察面向版本筹备会中的制作组成员，目标是帮助会议快速形成内容决策。

它不是单纯的统计面板，也不是替团队自动拍板的决策器。页面应该把信号整理成可讨论、可采纳、可追踪的建议。

每条洞察都要回答：

1. 玩家表现出了什么信号？
2. 这个信号意味着兴趣机会、理解风险，还是证据不足？
3. 制作组下一步可以做什么？
4. 这项动作面向谁、何时发布？
5. 发布后如何验证动作有效？

### 3.2 会议简报结构

页面内容按以下顺序组织：

#### 会议摘要

- 数据更新时间；
- 历史样本与近期增量；
- 当前是否接入站外趋势；
- 一句数据边界提醒。

#### 本次最值得讨论的三件事

只展示最重要的三条建议，每条建议先给结论，再展开证据。

建议分为三类：

- **放大**：已有明确兴趣，适合做 PV、社媒或预热内容；
- **解释**：兴趣存在但理解困难，适合 FAQ、时间线或关系图；
- **暂缓**：样本不足、证据不够或推测风险过高，暂不建议进入排期。

#### 理解风险

风险不是简单的负面评价，而是制作组发布内容时可能遇到的误读：

- 已确认事件被误读为最终目的；
- 人物、称号或关系被混淆；
- 暗示被传播成事实；
- 单一玩家群体的兴趣被误判为整体趋势。

每项风险必须同时给出缓解动作，例如增加 FAQ、补充事实边界或调整首次出现时的命名方式。

#### 证据工作台

证据区域保留当前的站内证据、站外趋势和数据说明标签，但内容要从“查看统计”转为“支持当前判断”。

每条建议至少绑定以下证据类型中的一种：

- 玩家提问频次；
- 预热专题选择；
- 时间线节点点击；
- 关系节点点击；
- 语言差异或玩家画像差异。

### 3.3 建议卡片字段

发行建议使用以下固定字段：

```text
建议类型：放大 / 解释 / 暂缓
主题：统一的发行主题名称
玩家信号：发生了什么
制作判断：为什么值得处理
建议动作：制作 FAQ、预热专题、关系图、PV 文案等
目标人群：新玩家、回归玩家、剧情党等
建议时机：第 1 周、第 2 周、第 3-4 周或继续观察
置信度：高 / 中 / 低
证据：可回溯的站内信号
验证方法：发布后观察什么变化
```

现有 `opportunityScore`、`riskScore` 和 `confidence` 继续作为规则引擎的内部依据，但页面优先展示会议语言，例如“优先处理”“需要补充解释”“暂时观察”，而不是让制作组自行解释分数。

### 3.4 样本与证据边界

- 样本不足时不得给出高置信度建议。
- 单一信号只说明局部兴趣，不说明整个玩家群体的趋势。
- 站外趋势未接入时，要明确说明当前结论只基于站内行为。
- AI 可以帮助润色判断和行动建议，但不能修改规则分数，也不能生成没有证据绑定的结论。

### 3.5 后续阶段能力

“待评审 / 已采纳 / 已验证”状态管理属于后续阶段，不作为第一阶段的硬要求。第一阶段先确保建议本身具备证据、动作和验证方法，避免先做工作流外壳而内容仍然空泛。

## 4. 两页共享的数据语言

预热专题、问题主题、时间线节点和关系图节点必须继续通过统一的发行主题映射关联。

同一个主题在两页中使用同一名称和 ID：

```text
预热专题 / 玩家提问 / 时间线节点 / 关系节点
                 ↓
          统一发行主题
                 ↓
       建议、风险、证据与验证
```

这样发行洞察中的“建议补充神之心 FAQ”才能直接回溯到玩家在哪个专题、哪个节点上产生了兴趣或理解断点。

## 5. 验收标准

### 版本预热

- 玩家能明确区分已确认、暗示线索和未解断点。
- 未解断点显示具体问题，但不泄露至冬版本答案。
- 三个专题从不同角度指向同一个版本级主悬念。
- 完整考据可以展开已实装证据，但不会把未来内容写成事实。
- 玩家能从断点自然进入相关提问或继续探索。

### 发行洞察

- 版本筹备会参与者能快速找到当前最重要的三条建议。
- 每条建议都包含信号、判断、动作、证据和验证方法。
- 页面能区分兴趣机会、理解风险和证据不足。
- 低样本和未接入站外趋势的限制会被明确表达。
- 建议不会替制作组做最终决策，而是提供可审议的行动草案。

## 6. 本轮不做

- 不重做首页首屏和至冬关系图谱的整体视觉。
- 不大幅重构导航或页面布局。
- 不接入站外趋势数据。
- 不新增复杂的建议审批工作流。
- 不把未实装至冬内容补写成确定事实。
